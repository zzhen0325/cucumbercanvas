# E2Eテストケース品質チェックリスト

このドキュメントでは、E2Eテストケースの品質を保証するためのチェックリストを定義します。
テストケース作成時・レビュー時にこのチェックリストを使用してください。

---

## 📋 テストケース品質チェックリスト

### 必須項目（Must Have） ✅

テストケースとして成立するための最低限必要な項目です。これらが欠けている場合、テストケースとして不完全です。

- [ ] **目的が明確**: 何を検証するのか1文で説明できる
  - ✅ 良い例: 「フォーム送信後、成功メッセージが表示されること」
  - ❌ 悪い例: 「フォームのテスト」「正常に動作すること」

- [ ] **前提条件が具体的**: テスト実行前の状態が明確に定義されている
  - ✅ 良い例: 「ユーザーが認証済み」「テストデータが1件作成されている」
  - ❌ 悪い例: 「ログイン済み」「データがある」

- [ ] **手順が再現可能**: 他の人が読んで同じ操作ができる
  - ✅ 良い例: 「1. 一覧画面で対象データの行をクリック」
  - ❌ 悪い例: 「1. データを開く」「1. 適当に操作する」

- [ ] **期待結果が検証可能**: 成功/失敗が明確に判定できる
  - ✅ 良い例: 「APIリクエスト（PUT `/api/items/{id}`）が送信されること」
  - ❌ 悪い例: 「正常に保存される」「エラーが出ない」

- [ ] **一意なテストID**: 他のテストと重複しないID（例: CRUD-001, AUTH-001）
  - ✅ 良い例: `CRUD-001`, `AUTH-001`, `SEARCH-001`
  - ❌ 悪い例: `TEST-001`, `001`, ID無し

---

### 推奨項目（Should Have） ⭐

テストケースの品質と保守性を高めるための推奨項目です。

- [ ] **優先度・リスクスコアの明記**: P0-P4とリスクスコアを記載
  - 例: 「**優先度**: P0」「**リスクスコア**: 20」

- [ ] **適切なタグ付け**: `@smoke`, `@critical`, `@regression`等のタグ
  - P0/P1 → `@smoke`, `@critical`
  - P2 → `@regression`
  - P3/P4 → `@optional`

- [ ] **実行時間の目安**: 長時間テスト（>30秒）は明示
  - 例: 「**実行時間**: 約45秒（複数API呼び出しあり）」

- [ ] **前提データの詳細**: 必要なテストデータが明確
  - 例: 「テストデータ: 名前=`Test-Item-XXX`, URL=`https://example.com`」

- [ ] **クリーンアップ方針**: テスト後の状態リセット方法
  - 例: 「テスト後、作成したデータを自動削除」

- [ ] **実装コード参照**: 実装済みテストのファイル名・行番号
  - 例: 「**実装コード**: `example.spec.ts:36-85`」

---

### 品質基準（Quality Criteria） 🎯

テストケースが満たすべき品質基準です。

#### 1. 独立性（Independence）
- [ ] **他のテストに依存しない**: 単独で実行可能
  - ✅ 良い: 各テストが自分でテストデータを作成
  - ❌ 悪い: 「CRUD-001の実行後に実行すること」という依存

#### 2. 冪等性（Idempotency）
- [ ] **何度実行しても同じ結果**: 実行順序に依存しない
  - ✅ 良い: 一意なID（タイムスタンプ + UUID）でテストデータ生成
  - ❌ 悪い: 固定のデータ名「テスト太郎」を使用（競合の可能性）

#### 3. 原子性（Atomicity）
- [ ] **1つの責務のみをテスト**: Single Responsibility Principle
  - ✅ 良い: 「データ作成のテスト」「データ更新のテスト」を分離
  - ❌ 悪い: 1つのテストで作成→更新→削除を全て検証

#### 4. 明確性（Clarity）
- [ ] **技術者でなくても理解できる**: ビジネス視点で記述
  - ✅ 良い: 「フォーム送信後、確認ダイアログが表示されること」
  - ❌ 悪い: 「onSubmitイベントハンドラーがモーダルコンポーネントをレンダリングすること」

#### 5. 保守性（Maintainability）
- [ ] **UIや実装の変更に強い**: Page Object Model等のパターン使用
  - ✅ 良い: `listPage.clickRow(itemName)`
  - ❌ 悪い: `page.locator('div.row:nth-child(3) > td').click()`

---

### アンチパターンチェック ⚠️

以下のアンチパターンに該当しないことを確認してください。

- [ ] ❌ **複数の機能を1つのテストで検証していない**
  - 悪い例: 「データの作成・更新・削除をまとめてテスト」
  - 理由: どこで失敗したか特定しづらい、保守性が低い

- [ ] ❌ **曖昧な期待結果でない**
  - 悪い例: 「正常に動作すること」「エラーが出ないこと」
  - 理由: 何が正常か定義されていない、検証不可能

- [ ] ❌ **特定の環境やデータに依存していない**
  - 悪い例: 「データID=123が存在すること」「開発環境のデータを使用」
  - 理由: 他の環境で実行できない、並列実行で競合

- [ ] ❌ **実行順序に依存していない**
  - 悪い例: 「この前に実行されたテストで作成されたデータを使用」
  - 理由: テストの並列実行や単独実行ができない

- [ ] ❌ **固定の待機時間を使用していない**
  - 悪い例: `await page.waitForTimeout(3000)` // 3秒待機
  - 理由: flaky testの原因、実行時間の無駄

- [ ] ❌ **脆弱なセレクターを使用していない**
  - 悪い例: `page.locator('div > div > div:nth-child(3)')`
  - 理由: DOM構造変更で簡単に壊れる

## 📝 テストケーステンプレート

以下のテンプレートを使用してテストケースを作成してください。

```markdown
### TEST-ID-XXX: テスト名

**優先度**: P0/P1/P2/P3/P4
**リスクスコア**: XX
**タグ**: `@smoke`, `@critical`, `@regression`, `@optional`

**目的**: [何を検証するのか1文で]

**前提条件**:
- [前提条件1]
- [前提条件2]

**テスト手順**:
1. [明確な操作手順1]
2. [明確な操作手順2]
3. [明確な操作手順3]

**期待結果**:
- [検証可能な期待結果1]
- [検証可能な期待結果2]

**実装コード**: `ファイル名.spec.ts:開始行-終了行`
```

## 🔍 レビュー時のチェックポイント

### レビュアー向けチェックリスト

テストケースをレビューする際は、以下の観点で確認してください。

#### 1. 仕様の正確性
- [ ] ビジネス要件を正しく反映しているか
- [ ] 実際のユーザー操作フローに沿っているか
- [ ] エッジケースを適切にカバーしているか

#### 2. テスト設計の妥当性
- [ ] リスクスコアと優先度は適切か
- [ ] テストピラミッド戦略に沿っているか（E2Eで本当に必要か）
- [ ] 他のテスト（統合・単体）で代替できないか

#### 3. 実装可能性
- [ ] 自動化可能なテストか（手動テストにすべきでないか）
- [ ] 必要な`data-testid`は特定されているか
- [ ] 並列実行可能な設計か

#### 4. 保守性
- [ ] 仕様変更時に修正しやすいか
- [ ] 他のテストと重複していないか
- [ ] ドキュメントが十分か

## 📊 品質メトリクス

以下のメトリクスで、テストケース全体の品質を測定します。

### 目標値

| メトリクス | 目標値 | 現在値 | 備考 |
|-----------|--------|--------|------|
| 必須項目充足率 | 100% | - | 全テストケースで必須項目を満たす |
| 推奨項目充足率 | 80%以上 | - | 推奨項目の充足を目指す |
| アンチパターン発生率 | 0% | - | アンチパターンを排除 |
| テストの独立性 | 100% | - | 全テストが単独実行可能 |
| テストの冪等性 | 100% | - | 実行順序に依存しない |

### 測定方法

- **必須項目充足率**: (必須項目を満たすテストケース数 / 全テストケース数) × 100%
- **推奨項目充足率**: (推奨項目を満たすテストケース数 / 全テストケース数) × 100%
- **アンチパターン発生率**: (アンチパターンを含むテストケース数 / 全テストケース数) × 100%

## 🚀 継続的改善

### 定期レビュー
- **月次**: テストケース品質メトリクスの確認
- **四半期**: チェックリストの見直しと更新

### フィードバックループ
- テスト失敗時: 原因がテストケースの品質問題か確認
- レビュー時: よくある問題をチェックリストに追加
