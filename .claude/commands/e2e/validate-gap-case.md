# E2E Test Case Gap Analysis

実装済み機能に対するテストケースのギャップ分析を実施します。テストケースが存在しない機能を特定します。

📖 **共通ルールと参照ドキュメントは `.claude/e2e-test-common.md` を参照してください。**
📖 **コーディング標準は `docs/coding-standard/playwright.md` を参照してください（リトライ禁止ポリシー等）。**
📖 **プロジェクト固有の設定は `.claude/e2e-config.md` を参照してください。**

## 事前確認: E2E環境の確認（必須）

**最初に以下を確認してください：**

```bash
ls docs/e2e/
```

**`docs/e2e/` ディレクトリが存在しない場合:**
- 以下のメッセージを表示して**このコマンドを終了**してください
- 他のタスクは実行しないでください

```
❌ E2E環境が初期化されていません。

先に /e2e:init を実行してE2E環境を初期化してください。

/e2e:init
```

**ディレクトリが存在する場合のみ、以降のタスクに進んでください。**

## 目的

1. **実装済み機能の抽出**: UIコンポーネント、APIエンドポイント、仕様書から機能を特定
2. **テストケースカバレッジの照合**: 各機能に対するテストケースの存在を確認
3. **リスク評価**: テストケースが存在しない機能のリスクを評価
4. **推奨テストケースの提案**: 不足しているテストケースを提案

## タスク

### 1. プロジェクト構造の検出

**最初にプロジェクト構造を確認してください。** プロジェクトによって構造は異なります。

```bash
# プロジェクトルートの構造を確認
ls -la

# 一般的なソースディレクトリを探索
ls -la src/ 2>/dev/null || true
ls -la pages/ 2>/dev/null || true
ls -la components/ 2>/dev/null || true
ls -la app/ 2>/dev/null || true
ls -la apps/ 2>/dev/null || true
ls -la api/ 2>/dev/null || true
```

**検出されたディレクトリ構造に基づいて、以降の分析対象パスを決定してください。**

### 2. 実装済み機能の抽出

検出されたプロジェクト構造に基づき、以下のソースから実装済み機能を特定します:

**UIコンポーネントの分析**:

検出された構造に応じて適切なパスを使用:
- モノレポ: `apps/frontend/pages/`, `apps/frontend/components/`
- 標準Next.js: `pages/`, `components/`, `app/`
- src構造: `src/pages/`, `src/components/`, `src/app/`

```bash
# 存在するディレクトリのみ分析（パスはプロジェクト構造に応じて調整）
# ページコンポーネントの一覧
ls -la [検出されたpagesディレクトリ]/

# コンポーネント内のユーザーインタラクション要素を抽出
grep -rn "onClick\|onSubmit\|onChange\|onBlur" [検出されたcomponentsディレクトリ]/
grep -rn "data-testid" [検出されたcomponentsディレクトリ]/
```

**APIエンドポイントの分析**:

検出された構造に応じて適切なパスを使用:
- Next.js API Routes: `pages/api/`, `app/api/`
- 分離API: `api/`, `apps/api/src/`, `server/`
- Express/Fastify: `src/routes/`, `routes/`

```bash
# 存在するディレクトリのみ分析（パスはプロジェクト構造に応じて調整）
# APIエンドポイントを抽出
grep -rn "router\.\(get\|post\|put\|patch\|delete\)" [検出されたAPIディレクトリ]/
grep -rn "export.*\(GET\|POST\|PUT\|PATCH\|DELETE\)" [検出されたAPIディレクトリ]/
grep -rn "app\.\(get\|post\|put\|patch\|delete\)" [検出されたAPIディレクトリ]/
```

**仕様書・要件定義からの機能抽出（存在する場合）**:

```bash
# Kiro仕様書の確認（存在する場合のみ）
ls -la .kiro/specs/ 2>/dev/null && cat .kiro/specs/*/requirements.md

# その他の仕様書（存在する場合）
ls -la docs/ 2>/dev/null || true
cat README.md 2>/dev/null || true
```

### 3. 機能カテゴリの分類

抽出した機能を以下のカテゴリに分類:

| カテゴリ | 説明 | 例 |
|---------|------|-----|
| **CRUD操作** | データの作成・読取・更新・削除 | ユーザー作成、ユーザー削除 |
| **検索・フィルタ** | データの検索、絞り込み | ユーザー検索、ステータスフィルタ |
| **フォーム操作** | 入力、バリデーション、送信 | 自動保存、入力検証 |
| **ナビゲーション** | ページ遷移、パネル操作 | スライドパネル、タブ切り替え |
| **データエクスポート** | CSV、PDF等の出力 | CSV出力、一括ダウンロード |
| **一括操作** | 複数データの同時処理 | 一括編集、一括削除 |
| **キーボード操作** | ショートカット、アクセシビリティ | Escape閉じ、Tab移動 |
| **連携機能** | 外部サービス連携 | URL自動リンク、ツール連携 |

### 4. テストケースカバレッジの照合

各機能に対して、テストケースの存在を確認:

**テストケースファイルの読み込み**:
```bash
# テストケースディレクトリの確認
ls -la docs/e2e/test-cases/

# 各テストケースファイルを読み込み
cat docs/e2e/test-cases/*.md
```

**マッチングロジック**:
- 機能名とテストケースの目的・テスト名を比較
- コンポーネント名とテストケースのカテゴリを比較
- APIエンドポイントとテストケースの前提条件・手順を比較

### 5. リスク評価

テストケースが存在しない機能のリスクを評価:

| リスクレベル | 基準 | 例 |
|-------------|------|-----|
| 🔴 高 | データ損失・セキュリティ・全ユーザー影響 | 削除機能、認証、決済 |
| 🟡 中 | 主要ユーザーフロー・UX影響 | 検索、フィルタ、フォーム |
| 🟢 低 | エッジケース・限定的影響 | エラー表示、空状態 |

**前提条件**: 複数のユーザーデータが存在する
**テスト手順**:
1. ユーザー一覧画面を開く

**期待結果**:
- 選択したユーザーが削除される
- 削除完了トースト通知が表示される
- 一覧から削除したユーザーが消える
