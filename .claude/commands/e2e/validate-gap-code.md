# E2E Test Code Gap Analysis

テストケースに対するテストコードのギャップ分析を実施します。

📖 **共通ルールと参照ドキュメントは `.claude/e2e-test-common.md` を参照してください。**
📖 **コーディング標準は `docs/coding-standard/playwright.md` を参照してください（リトライ禁止ポリシー等）。**
📖 **プロジェクト固有の設定は `.claude/e2e-config.md` を参照してください。**

## 事前確認: E2E環境の確認（必須）

**最初に以下を確認してください：**

```bash
ls docs/e2e/
```

**`docs/e2e/` ディレクトリが存在しない場合:**
- 以下のメッセージを表示して**このコマンドを終了**してください
- 他のタスクは実行しないでください

```
❌ E2E環境が初期化されていません。

先に /e2e:init を実行してE2E環境を初期化してください。

/e2e:init
```

**ディレクトリが存在する場合のみ、以降のタスクに進んでください。**

## 目的

1. **テストケース準拠性チェック**: 作成済みテストケースが `.claude/commands/e2e/case-generate.md` のルールに準拠しているか確認
2. **コーディング標準準拠性チェック**: 実装済みテストコードが `docs/coding-standard/playwright.md` に準拠しているか確認
3. **実装とテストケースの一致性チェック**: テストコードがテストケース仕様と一致しているか確認
4. **実装ギャップ分析**: 未実装のテストケース、不完全な実装を特定

## タスク

### 1. テストケースドキュメントの読み込み

まず、全テストケースドキュメントを読み込みます。

```bash
# テストケースディレクトリの確認
ls -la docs/e2e/test-cases/
```

各カテゴリのテストケースファイルを読み込む:
- `docs/e2e/test-cases/index.md` - 全体概要
- `docs/e2e/test-cases/*.md` - 各カテゴリのテストケース

**抽出パターン**:
- Test ID: `| [A-Z]+-[0-9]{3} |` 形式（例: `CRUD-001`, `AUTO-TEXT-001`）
- テスト名: Test IDと同じ行の次のカラム
- 優先度: `**優先度**: P[0-4]` のパターン
- カテゴリ: ファイル名から推定（例: `crud.md` → 「CRUD操作」）

### 2. 実装済みテストファイルの確認

```bash
# Playwrightテストファイルの一覧
ls -la playwright-tests/tests/
```

**実装済み判定パターン**:
```typescript
test('TEST-ID: テスト名', async ({ page }) => ...)
test.describe('カテゴリ', () => {
  test('TEST-ID: テスト名', ...)
})
```

**スキップ判定**: `test.skip()` または `@skip` タグがある場合は未実装扱い

### 3. 進捗管理ファイルとの照合

`docs/e2e/progress.md` を参照し、以下を確認:
- 実装ステータス（✅ 完了 / ⏸️ スキップ / 未記載）
- テスト結果（✅ 合格 / ❌ 失敗 / 未実行）

### 4. テストケース準拠性チェック

各テストケースドキュメントについて、以下をチェック:

#### ✅ 必須項目チェック

**テストケース構造 (`case-generate.md` 準拠)**:
- [ ] **Test ID**: 一意のテストIDが付与されているか (例: `CRUD-001`, `AUTO-TEXT-001`)
- [ ] **テスト名**: 明確で具体的なテスト名があるか
- [ ] **目的**: テストの目的が明記されているか
- [ ] **前提条件**: テスト実行前の状態が定義されているか
- [ ] **テスト手順**: ステップバイステップの手順が記載されているか
- [ ] **期待結果**: 各ステップの期待結果が明確か
- [ ] **優先度**: P0-P4の優先度が設定されているか
- [ ] **タグ**: `@smoke`, `@regression` などのタグが適切か

#### ⚠️ 品質チェック

**テストケースの独立性**:
- [ ] テストが他のテストに依存していないか
- [ ] テストデータの準備とクリーンアップが適切か

**テストケースの原子性**:
- [ ] 1つのテストケースが1つの機能をテストしているか
- [ ] テストが複雑すぎないか（分割すべきでないか）

**テストケースの明確性**:
- [ ] 誰が読んでも理解できる記述か
- [ ] 曖昧な表現がないか

### 5. コーディング標準準拠性チェック

実装済みテストコードについて、`docs/coding-standard/playwright.md` に基づいてチェック:

#### ✅ 構造とパターン

**Page Object Model**:
- [ ] Page Objectパターンを使用しているか
- [ ] UI要素のセレクタがPage Objectに分離されているか
- [ ] テストロジックとUI実装が分離されているか

**test.step() の使用**:
- [ ] 複雑なテストで `test.step()` を使用しているか
- [ ] ステップ名が明確で意味があるか

**test.describe() のグループ化**:
- [ ] 関連するテストが適切にグループ化されているか
- [ ] グループ名が機能やカテゴリを反映しているか

#### ✅ セレクタ戦略

**data-testid の使用**:
- [ ] `data-testid` を優先的に使用しているか
- [ ] テキストベースのセレクタは適切な場合のみ使用しているか
- [ ] CSSセレクタやXPathの使用が最小限か

**セレクタの安定性**:
- [ ] 実装変更に強いセレクタを使用しているか
- [ ] 脆弱なセレクタ（nth-child, indexなど）を避けているか

#### ✅ 待機戦略

**適切な待機方法**:
- [ ] `waitForTimeout()` を使用していないか
- [ ] `waitForSelector()`, `waitForResponse()` などの明示的な待機を使用しているか
- [ ] `expect().toBeVisible()` などのアサーション付き待機を使用しているか

**ネットワークリクエストの待機**:
- [ ] API呼び出しを含むアクションで `waitForResponse()` を使用しているか
- [ ] レースコンディションを回避しているか

#### ✅ リトライ禁止ポリシー

- [ ] `retries` 設定が0になっているか
- [ ] `expect.toPass()` を使用していないか
- [ ] カスタムリトライロジックを使用していないか

#### ✅ E2Eテスト原則（ブラウザ vs API）

**ブラウザ操作優先**:
- [ ] 機能テストはブラウザ操作を通じて実施しているか
- [ ] API直接呼び出しはテストデータ準備/クリーンアップのみか
- [ ] UI操作の検証をAPIで代替していないか

**禁止パターンのチェック**:
```typescript
// ❌ API直接テスト（禁止）
test('ユーザー作成', async ({ request }) => {
  const response = await request.post('/api/users', { data: {...} });
  expect(response.status()).toBe(201);
});

// ✅ ブラウザ操作テスト（推奨）
test('ユーザー作成', async ({ page }) => {
  await page.getByTestId('create-button').click();
  await page.getByTestId('name-input').fill('テストユーザー');
  await page.getByTestId('save-button').click();
  await expect(page.getByText('ユーザーを作成しました')).toBeVisible();
});
```

#### ✅ エラーハンドリング

**適切なアサーション**:
- [ ] `expect()` を使用した明確なアサーションがあるか
- [ ] カスタムエラーメッセージが必要な箇所で使用されているか

**失敗時の情報**:
- [ ] スクリーンショット、トレース、ビデオが有効化されているか

#### ✅ テストデータ管理

**テストデータの独立性**:
- [ ] 各テストが独自のテストデータを使用しているか
- [ ] タイムスタンプやUUIDで一意性を確保しているか

**クリーンアップ**:
- [ ] テスト後のデータクリーンアップが実装されているか
- [ ] `try-finally` でクリーンアップを保証しているか

### 6. 実装とテストケースの一致性チェック

テストケースドキュメントと実装コードを比較:

#### ✅ カバレッジチェック

**Test ID マッピング**:
- [ ] 各テストケースのTest IDに対応する実装があるか
- [ ] 実装されたテストがテストケース仕様に記載されているか

**テスト手順の一致**:
- [ ] 実装がテストケースの手順通りに実行されているか
- [ ] 期待結果がコードで検証されているか

**前提条件の実装**:
- [ ] テストケースの前提条件が `beforeEach` または事前ステップで実装されているか

#### ⚠️ 実装の逸脱チェック

**仕様外の実装**:
- [ ] テストケースにない検証を追加していないか
- [ ] 仕様と異なる手順で実装していないか

**不完全な実装**:
- [ ] テストケースの一部のステップが実装されていないか
- [ ] 期待結果の一部が検証されていないか

### 7. 不整合の検出

以下の不整合があれば警告を表示:

**⚠️ 警告例**:
```
⚠️ 不整合が検出されました:

1. progress.mdで「実装済み」だがコードが見つからないテスト (3件)
   - FILTER-005: フィルタ削除後の確認
   - TAG-003: タグの並び替え機能
   - POSITION-007: ポジション無効化

2. コードにあるがテストケース仕様書にないテスト (2件)
   - EXPERIMENTAL-001: playwright-tests/tests/experimental.spec.ts:45
   - DEBUG-001: playwright-tests/tests/debug.spec.ts:12

3. progress.mdに記載がないテスト (1件)
   - CONNECTION-004: 接続設定のバリデーション
```

### 8. 違反の自動検出パターン

以下のパターンを検出し、レポートに含めます:

#### コーディング標準違反パターン

```bash
# waitForTimeout() の使用を検出
grep -rn "waitForTimeout" playwright-tests/tests/

# API直接テストパターンを検出（request のみでページ操作なし）
grep -rn "async ({ request })" playwright-tests/tests/

# Page Objectパターン未使用を検出（page.locator が直接テストに記述）
grep -rn "page.locator\|page.getByRole\|page.getByTestId" playwright-tests/tests/*.spec.ts

# waitForLoadState('networkidle') の使用を検出（非推奨）
grep -rn "waitForLoadState.*networkidle" playwright-tests/tests/

# expect.toPass() の使用を検出（リトライ禁止）
grep -rn "expect.*toPass" playwright-tests/tests/

# retries 設定を検出
grep -rn "retries:" playwright-tests/
```

#### テストケース準拠性違反パターン

```bash
# Test IDが付与されていないテストケースを検出
grep -L "^| [A-Z]+-[0-9]+ |" docs/e2e/test-cases/*.md

# 優先度が設定されていないテストケースを検出
grep -L "P[0-4]" docs/e2e/test-cases/*.md
```

## 注意事項

- このコマンドはテストの実行は行いません（静的分析のみ）
- 実際のテスト実行は `/e2e:steering` コマンドを使用してください
- 分析結果は定期的に実行し、品質を維持してください
