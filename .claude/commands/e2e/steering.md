# E2E Test Execution and Progress Update

E2Eテストを実行し、進捗状況を更新します。

📖 **共通ルールと参照ドキュメントは `.claude/e2e-test-common.md` を参照してください。**
📖 **コーディング標準は `docs/coding-standard/playwright.md` を参照してください（リトライ禁止ポリシー等）。**
📖 **プロジェクト固有の設定は `.claude/e2e-config.md` を参照してください。**

## 事前確認: E2E環境の確認（必須）

**最初に以下を確認してください：**

```bash
ls docs/e2e/
```

**`docs/e2e/` ディレクトリが存在しない場合:**
- 以下のメッセージを表示して**このコマンドを終了**してください
- 他のタスクは実行しないでください

```
❌ E2E環境が初期化されていません。

先に /e2e:init を実行してE2E環境を初期化してください。

/e2e:init
```

**ディレクトリが存在する場合のみ、以降のタスクに進んでください。**

## タスク

### 0. 認証リフレッシュ（冪等性確保）- 認証が必要な場合のみ

**まず `.claude/e2e-config.md` の「認証が必要」設定を確認してください。**

**認証が必要な場合（`認証が必要: true`）:**
- テスト実行前に認証トークンをリフレッシュして、認証切れによるテスト失敗を防ぎます
- `.claude/e2e-config.md` の「認証更新コマンド」を実行してください

**認証が不要な場合（`認証が必要: false`）:**
- このステップをスキップして、次のステップに進んでください

### 1. サーバー起動の確認

E2Eテストは**本番環境に近い状態**で実行する必要があります。開発サーバー（Hot Reload有効）ではなく、プロダクションビルドを使用することを推奨します。

**重要**: サーバーの起動・停止は**自動で実行しないでください**。ユーザーに確認・依頼してください。

**サーバーが起動していない場合の対応:**
1. ユーザーにサーバー起動を依頼
2. 起動コマンドは `.claude/e2e-config.md` の「ビルド＆起動コマンド」または「開発サーバー起動コマンド」を参照
3. 例: 「E2Eテストを実行するにはサーバーが必要です。起動してください。」

**プロダクションビルドを推奨する理由**:
- Hot Reloadによるタイミング問題を回避
- 本番環境と同じコードパスでテスト
- ビルドエラーを事前に検出
- テスト結果の再現性を向上

### 2. E2Eテスト実行

```bash
npx playwright test --reporter=list
```

### 3. 進捗ドキュメント更新

最新の実装状況とテスト実行結果に基づき`docs/e2e/progress.md`を更新します。

**重要**: `progress.md`には**最新の結果のみ**を記載します。履歴は別ファイルに保存されます。

**テーブル形式**（`.claude/e2e-test-common.md`の「進捗管理フォーマット」参照）:

| Test ID | テスト名 | 目的 | 実装ステータス | テスト結果 |
|---------|---------|------|--------------|-----------|

**テーブル後に詳細記載**:
- ❌ 失敗したテスト: エラー内容、原因分析、修正案
- ⚠️ 未完了の実装: 残作業、ブロッカー、完了見込み

### 3.5 履歴ファイルの作成（変更があった場合のみ）

前回実行結果と差分がある場合、`docs/e2e/histories/`に履歴ファイルを作成します。

**ファイル名形式**: `YYYY-MM-DD_HHmmss.md`（例: `2025-11-30_103045.md`）

**履歴ファイルの内容**:
- 実行日時
- サマリー（合格/失敗/スキップ数）
- 前回との差分
- 失敗テストの詳細分析
- 修正内容（ある場合）

```markdown
# E2Eテスト実行履歴 - 2025-11-30 10:30:45

## サマリー
- 総テスト数: 104
- 合格: 104 (100%)
- 失敗: 0 (0%)

## 前回との差分
- AUTO-DATE-005: ❌ FAIL → ✅ PASS

## 修正内容
### AUTO-DATE-005 修正
MUI DatePickerの「Today」ボタンではなく、gridcellを直接クリックするように変更。
```

### 4. 差分サマリーの出力

タスク完了時、前回実行結果との差分をサマリーして標準出力に表示します。

**差分比較項目**:
1. 実装ステータスの変化(未実装 → 実装中 → 完了)
2. テスト結果の変化(✅ PASS ↔ ❌ FAIL)
3. カテゴリー別統計(合格率の変化)
4. 全体統計(実装完了率、合格率)

**出力例**:

```
## 📊 E2Eテスト実行結果サマリー

### 前回との差分

#### ステータス変化
- TC-AUTO-TEXT-003: 未実装 → 完了
- TC-AUTO-TEXT-004: 実装中 → 完了

#### テスト結果変化
- TC-AUTO-TEXT-003: - → ✅ PASS
- TC-AUTO-TEXT-004: ❌ FAIL → ✅ PASS

#### カテゴリー別統計
- Auto-save (Text): 3/5 → 5/5 PASS (60% → 100%) [+2]

### 全体統計
- 実装完了: 28/44 → 30/44 (64% → 68%) [+2]
- テスト合格: 25/28 → 28/30 (89% → 93%) [+3/+2]
```

**差分抽出方法**:
1. タスク開始時に`docs/e2e/progress.md`の内容を保存
2. 更新後、新旧のテーブルを行単位で比較
3. 変更があった項目のみ表示(変化なしは省略)

## 注意事項

- テスト設計やテストケース仕様は更新しない（それぞれ専用のドキュメントで管理）
- 実装状況とテスト結果のみを`docs/e2e/progress.md`に記載
- **リトライは使用しない**: `docs/coding-standard/playwright.md`のリトライ禁止ポリシーに従い、`--retries`オプションやテスト内でのリトライロジックは使用しないこと。テストが失敗した場合は、その結果をそのまま記録し、原因を分析する
- **テストコードの修正はこのコマンドでは行わない**: 失敗したテストの修正が必要な場合は、原因分析と修正案を`docs/e2e/progress.md`に記録した後、`/e2e:code-generate`を実行してください

## テスト失敗時のフロー

```
1. /e2e:steering        → テスト実行、失敗を検出、原因分析を記録
2. /e2e:code-generate   → 失敗したテストのコード修正
3. /e2e:qg-code         → 修正後の品質検査
4. /e2e:steering        → 再テスト実行、進捗更新
```
